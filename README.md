# tsk

> **Built entirely by AI.** Every line of code, every test, and this
> documentation were generated by AI coding agents (Claude Code) under human
> direction. **This is alpha/testing software**: expect bugs and rough edges,
> back up your data before you rely on it, and use it with no warranty of
> any kind.

A vim-native, keyboard-only terminal kanban board and quick note taker.
Three fixed columns (ToDo / Doing / Done), multiple boards, local SQLite
storage, and optional password-protected boards whose database file is
itself encrypted.

Current release: **v0.1.0-alpha.1** (alpha/testing — the first tagged
release).

## Features

- **Vim-native keybindings**: modal navigation, counts (`3j`), two-key
  sequences (`gg`, `dd`, `ZZ`), no mouse support anywhere.
- **Kanban board**: ToDo / Doing / Done columns with live counts, arrow-key
  or `hjkl` navigation.
- **Cards coloured by deadline**, not status — status is already shown by
  the column a card sits in. See [Deadline colours](#deadline-colours).
- **ToDo/Doing sort automatically by deadline** (soonest/most-overdue on
  top); **Done sorts by completion time**, newest first. Manual reorder
  (`J`/`K`) only swaps cards that share the same sort key.
- **Auto-archive**: a Done card older than 5 days drops off the board (it
  stays in the database) and is reachable through the archive browser (`A`),
  which supports live text filtering.
- **Multiple boards**, switchable with `b` or `<Space>b`; create, rename,
  and delete from the same menu.
- **Encrypted boards**: any board can be password-protected. Its database is
  a separate SQLCipher file, keyed with an Argon2id-derived key — see
  [Encrypted boards](#encrypted-boards).
- **Tags, priority, notes**: per-task tags with a picker (toggle or create
  in place), priority levels, a searchable notes pane, and a one-line quick
  capture that can later be promoted to a task.
- **Live search** (`/`) over title, body, and tags, with `n`/`N` to jump
  matches.
- **External editor** for task bodies (`o`), opened as a floating popup
  inside tmux, or a full-screen suspend outside it.
- **Undo/redo** for structural edits (moves, deletes, reorders).
- **Single binary**: SQLCipher and OpenSSL are vendored and statically
  linked, so the binary does not depend on the system's OpenSSL/SQLite.

## Requirements

- **Rust via [rustup](https://rustup.rs)**, not your distribution's
  package. Debian's `apt` `rustc` (1.85) is too old for this project's
  dependencies (`ratatui`, `rusqlite`). Install with:

  ```sh
  curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
  ```

- A C compiler, `make`, and **`perl`** — needed to build the vendored
  SQLCipher/OpenSSL. On Debian/Ubuntu/Mint:

  ```sh
  sudo apt install build-essential perl
  ```

## Install

```sh
./install.sh                        # build (release) + install to ~/.local/bin
./install.sh --prefix /usr/local    # system-wide (needs sudo for the target directory)
./install.sh --uninstall            # remove the installed binary, keep your data
./install.sh --debug                # faster build, larger/slower binary
```

The release build vendors and statically links SQLCipher and OpenSSL, so
the resulting binary has no `libssl`/`libcrypto`/`libsqlite3` dependency.
It is still linked against glibc, so a binary built on a newer distribution
may not run on an older one — build with `./install.sh` on each machine.
`install.sh` warns if the binary picked up a dynamic OpenSSL/SQLite
dependency, and warns separately if tmux truecolor isn't reaching the
terminal (see [tmux](#tmux)).

## Usage

```sh
tsk                                  # open the default board
tsk --board work                     # open a specific board by name
tsk --config /path/to/config.toml    # use a specific config file
tsk --db-dir /path/to/data           # use a specific data directory
```

| Flag | Short | Description |
|---|---|---|
| `--config <FILE>` | `-c` | Path to the config file, overriding the default location |
| `--db-dir <DIR>` | `-d` | Directory holding the task database, overriding the default location |
| `--board <NAME>` | `-b` | Board to open on startup |

`tsk --help` / `tsk --version` work as usual.

## Keybindings

`h`/`l` or `←`/`→` — switch column · `j`/`k` or `↑`/`↓` — move selection
(counts work, e.g. `3j`) · `gg`/`G` — top/bottom · `Ctrl-d`/`Ctrl-u` — half
page · `Tab` — switch pane · `a`/`i` — new task or note · `e` or `Enter` —
edit · `o` — open body in the external editor · `H`/`L` — move task to the
previous/next column · `J`/`K` — reorder within the column · `m` or `S` —
status dropdown · `p` — priority dropdown · `t` — tag dropdown · `dd` —
delete · `c` — quick-capture a note · `N` — toggle the notes pane · `gp` —
promote a note to a task · `b` or `<Space>b` — board switcher (`a`/`A` to
create a plain/locked board, `dd`/`D` to delete the highlighted one) ·
`A` — archive browser (type to filter, `Enter` to open) · `u`/`Ctrl-r` —
undo/redo · `/` — search (`n`/`N` next/previous match, `Esc` or `:nohl` to
clear) · `:` — command line · `?` — help · `ZZ` — quit.

In the notes pane, `a`/`e`/`dd` act on notes instead of tasks.

Command line (`:`): `:board` (menu: new / new locked / rename current /
delete… / switch… / lock), `:board new <name> [locked]`, `:board rename
<name>`, `:board delete <name>`, `:lock` (lock the current board), `:e` or
`:reload` (re-read the database from disk), `:nohl` (clear search
highlighting), `:q` (quit).

Run `?` inside the app for the full, up-to-date list — it is generated from
the same binding table that drives key dispatch, so it cannot drift from
what the keys actually do.

## Configuration

Copy [`config.example.toml`](config.example.toml) to
`~/.config/tsk/config.toml` and edit it — every key is optional and the
shipped values are the defaults.

Paths are resolved in this order, highest priority first:

1. CLI flag (`--config`/`--db-dir`)
2. Environment variable (`TSK_CONFIG`/`TSK_DB_DIR`)
3. Config file value (`db_dir`, for the database directory only)
4. XDG default (`~/.config/tsk/config.toml`, `~/.local/share/tsk`)

Key options:

- `db_dir` — where the databases live. Keep this **out of a synced folder**
  (Dropbox, Nextcloud, Syncthing…) unless you also set `journal_mode =
  "delete"` — see [Syncing with Dropbox](#syncing-with-dropbox).
- `journal_mode` — `"wal"` (default) or `"delete"`. WAL splits each
  database into three files (`.db`, `-wal`, `-shm`) that a sync tool can
  replace independently and out of step with each other; `"delete"` keeps
  everything in one self-contained `.db` file between writes, which is what
  a synced directory needs.
- `default_board` — board to open at startup; if unset, the first board
  opens.
- `editor` — external editor for task bodies. Resolution order: an explicit,
  non-empty `editor` in this file, then **`nvim`** if it's on `PATH`, then
  `$VISUAL`, then `$EDITOR`, then `vim` as a last resort. `nvim` is
  deliberately checked before the environment variables: on many machines
  `$EDITOR`/`$VISUAL` are unset, and falling through to them first would
  silently land you on `vi`/`nano` instead.
- `lock_on_board_switch` — drop an unlocked board's key when you switch
  away from it (default `true`).
- `confirm_delete` — ask before deleting a task, note, or board (default
  `true`).
- `show_keyhints` — show the key-hint bar along the bottom of the screen
  (default `true`).
- `[theme]` — colours for columns, priorities, chrome, and the six
  deadline colours below. Values are an ANSI name (`"red"`, `"darkgray"`,
  `"white"`, …), `"reverse"`, or a hex value like `"#ff8700"`. Hex degrades
  automatically: exact RGB on a truecolor terminal, nearest 256-colour
  otherwise, then nearest basic colour.

## Deadline colours

A card's colour is driven by its **deadline**, not its status — the column
already shows status:

| Condition | Colour | Config key |
|---|---|---|
| No due date | grey | `deadline_none` |
| More than 15 days out | green | `deadline_distant` |
| 14–5 days out | yellow | `deadline_soon` |
| 4–2 days out | orange | `deadline_near` |
| Less than 2 days out | red | `deadline_imminent` |
| Overdue | white on purple | `deadline_overdue_fg` / `deadline_overdue_bg` |

Cards show a right-aligned deadline badge (`3d`, or `-2d` when overdue). All
six colours are configurable under `[theme]` in your config file.

In a task form, **Start** displays today and defaults to the task's actual
creation time. Set **TimeExpected** to derive the deadline automatically
from that timestamp. Enter a duration as minutes, hours, or days (`10m`,
`4h`, `15d`); a bare number means minutes. Saving after changing either
value recalculates the deadline.

## Encrypted boards

Any board can be created locked (`:board new <name> locked`, or `A` in the
board switcher). A locked board's tasks and notes live in their own
SQLCipher database file, separate from the main database, keyed by a
32-byte key derived from your passphrase with **Argon2id** (64 MiB memory,
3 passes, 1 lane) and a random 16-byte salt.

`main.db` — the plaintext database that holds every unlocked board — stores
only a locked board's **name, file path, and KDF salt**; it never stores
task or note content, or even a count, for a board you haven't unlocked.
The salt itself isn't secret and is fine to keep in the clear.

Neither the passphrase nor the derived key is kept after a board is
unlocked — only the open database connection. Locking a board (`:lock`, or
automatically on switch when `lock_on_board_switch` is set) closes that
connection, and the passphrase must be entered again to reopen it.

## Syncing with Dropbox

`tsk` can share one set of boards between two machines through a synced
folder (Dropbox, Syncthing, etc.), with two conditions:

1. Set **`journal_mode = "delete"`** in the config file that points at the
   synced directory. This keeps every database as one self-contained file
   between writes instead of the default WAL mode's three-file layout,
   which a sync tool can otherwise replace out of step and corrupt.
2. **Never run `tsk` against the same synced directory on two machines at
   once.** `tsk` detects when the database file has changed on disk (for
   example, Dropbox replacing it with the other machine's copy) and
   reloads automatically, but this is a safety net for switching machines
   in sequence, not a substitute for real concurrent-write safety. Let the
   sync client finish (Dropbox showing "Up to date") before opening `tsk`,
   and **quit with `ZZ`** before switching machines so your last writes are
   flushed and synced.

A Dropbox "conflicted copy" produced by editing offline on both machines at
once is not detected or merged — avoid concurrent offline edits.

## tmux

`tsk` degrades truecolor to 256 or 16 colours automatically when the
terminal doesn't advertise it, which is normal inside tmux by default:
`default-terminal` is often `screen-256color`, and a `Tc`
`terminal-overrides` entry that only matches `xterm-256color*` never takes
effect for it. To get truecolor inside tmux, add one of these to
`~/.tmux.conf` (newer tmux, recommended):

```
set -as terminal-features ',*:RGB'
```

or, for older tmux, match whatever `default-terminal` is actually set to:

```
set -ga terminal-overrides ',screen-256color:RGB'
```

`install.sh` checks for this mismatch and warns if it finds one.

The external editor (`o`) opens as a `tmux display-popup` over the
still-drawn board when `$TMUX` is set, titled with the task's name; outside
tmux it falls back to a full-screen suspend/restore.
